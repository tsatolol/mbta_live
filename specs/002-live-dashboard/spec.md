# 機能仕様: リアルタイム画面（Live Dashboard）

**feature ブランチ**: `002-live-dashboard`
**作成日**: 2026-11-01
**状態**: 下書き（Draft）
**入力**: 収集した最新データ（001）を使い、地図上の車両位置、駅ごとの到着予測、運行アラート、収集の稼働状況をブラウザで見られるようにする。

## ユーザーシナリオとテスト（User Scenarios & Testing）*（必須）*

### ユーザーストーリー 1 - 地図で全路線の列車の位置を見る（優先度: P1）

運行を監視する人として、地図上で全路線の列車が今どこにいて、どちらへ向かっているかを一目で見たい。

**この優先度の理由**: ダッシュボードの入口となる画面で、運行の乱れ（列車が固まっている、来ない区間がある）を直感的に把握できる。

**単独での確認方法**: 現在値テーブルにフィクスチャの車両を入れ、地図に路線と車両が表示され、15 秒ごとに更新されることを確認する。

**受け入れシナリオ**:

1. **前提** 運行中の車両がある, **操作** 地図を開く, **結果** 各路線が路線色で描かれ、車両が進行方向を向いた矢印で表示される
2. **前提** 地図を開いている, **操作** 路線フィルタで路線を切り替える, **結果** 選んだ路線の路線形状と車両だけが表示される
3. **前提** 地図を開いている, **操作** 車両をクリックする, **結果** 路線・行先・次の駅・状態・何秒前の情報かがポップアップで表示される
4. **前提** 位置情報が 3 分以上更新されていない車両, **操作** 地図に表示される, **結果** 灰色で表示される

---

### ユーザーストーリー 2 - 駅を選んで次の列車を見る（優先度: P1）

利用者・監視する人として、駅を選んで、方向ごとに次の列車があと何分で来るかを見たい。

**単独での確認方法**: 予測のフィクスチャを入れ、駅のページで方向別に次の 3 本が「n min」で表示され、時間の経過とともにカウントダウンすることを確認する。

**受け入れシナリオ**:

1. **前提** 駅の一覧, **操作** 駅名で検索する, **結果** 該当する駅が路線ごとにまとまって表示される
2. **前提** 駅のページを開いている, **操作** 予測がある, **結果** 方向ごとに次の 3 本が「n min」で表示され、ページを再読み込みしなくても毎秒カウントダウンする
3. **前提** 始発駅, **操作** 駅のページを開く, **結果** 到着予定時刻の代わりに出発予定時刻で表示される
4. **前提** 運休の便がある, **操作** 駅のページを開く, **結果** その便は `Cancelled` と表示される。通過（`SKIPPED`）の便は表示しない
5. **前提** その駅や路線に有効なアラートがある, **操作** 駅のページを開く, **結果** アラートも表示される

---

### ユーザーストーリー 3 - 有効な運行アラートを一覧で見る（優先度: P2）

監視する人として、今有効な遅延・運休・工事などのアラートを路線ごとに一覧したい。過去のアラートも検索したい。

**受け入れシナリオ**:

1. **前提** 有効なアラートがある, **操作** アラートの画面を開く, **結果** 路線ごとに重要度の高い順で、影響の種類（effect）のバッジ付きで表示される
2. **前提** まだ始まっていない予告のアラート, **操作** アラートの画面を開く, **結果** 有効なアラートとは区別して表示される
3. **前提** 過去のアラート, **操作** 期間・路線・種類で検索する, **結果** 該当するアラートが表示される

---

### ユーザーストーリー 4 - データが新しいかどうかが分かる（優先度: P2）

監視する人として、表示されているデータがいつの時点のものか、収集が止まっていないかを常に知りたい。

**受け入れシナリオ**:

1. **前提** どの画面でも, **操作** 画面を見る, **結果** ヘッダーに最終更新時刻（ボストン時間）が表示される
2. **前提** 最後に収集に成功してから 3 分以上経った, **操作** 画面を見る, **結果** `Live data is stale` という警告バナーが出る
3. **前提** 稼働状況の画面, **操作** 開く, **結果** 直近の収集の結果、レート制限の残量、DB のデータ量が表示される

### 境界ケース（Edge Cases）

- 運行時間外（車両も予測も 0 件）でも画面は正常に表示され、「運行時間外」と分かる
- 車両の `stop` が `null` のとき、ポップアップの「次の駅」は空欄にする
- 予測の到着予定時刻がすでに過ぎている便は表示しない
- dev 環境では、ヘッダーに `DEV` バッジを出す

## 要件（Requirements）*（必須）*

### 機能要件（Functional Requirements）

- **FR-001**: システムは、地図上に対象 8 路線の路線形状を路線色で描き、運行中の車両を進行方向付きで表示しなければならない（15 秒ごとに更新）
- **FR-002**: システムは、路線ごとに表示を切り替えられなければならない
- **FR-003**: システムは、駅の一覧と検索を提供しなければならない
- **FR-004**: システムは、駅ごとに方向別の次の 3 本を「n min」で表示し、ブラウザ側でカウントダウンしなければならない（30 秒ごとにデータを更新）
- **FR-005**: システムは、有効なアラートを路線別・重要度順に表示し、予告のアラートと区別し、過去のアラートを検索できなければならない
- **FR-006**: システムは、全画面のヘッダーに最終更新時刻を表示し、収集が 3 分以上止まったら警告しなければならない
- **FR-007**: システムは、収集の稼働状況を表示する画面を提供しなければならない
- **FR-008**: システムは、画面のフッターに MBTA の出典表記と地図タイルの帰属表示を出さなければならない
- **FR-009**: システムは、ブラウザから MBTA API を直接呼んではならない。すべて自前の API 経由で DB を読む
- **FR-010**: 画面の言語は英語、時刻はボストン時間（`America/New_York`）で表示しなければならない
- **FR-011**: システムへのアクセスは、許可したユーザーだけに制限されなければならない（仕組みは `specs/004-infra-cicd/`）

### テスト要件（Testing Requirements）

- **TR-001（内部 API）**: 各内部 API を、シードした本物の PostgreSQL に対して呼ぶ結合テストを書く。応答が共有の zod スキーマで解析できること、不正なクエリパラメータに 400 を返すこと、`SKIPPED` と過ぎた便が除かれること、始発駅で出発時刻が使われることを確かめる
- **TR-002（計算する値）**: `isStale`、アラートの状態（`active` / `upcoming` / `past`）、あと何分かの計算を、時計を固定して単体テストする
- **TR-003（画面: E2E）**: 次の状態を Playwright で確かめる: 地図に路線と車両が出る、路線フィルタ、車両のポップアップ、更新の止まった車両が灰色、駅の検索と到着表示、`Cancelled` の表示、運行時間外の表示、収集が 3 分止まったときの stale バナー、アラートの一覧、稼働状況、フッターの出典表記、dev の環境バッジ
- **TR-004（MBTA API を呼ばないこと）**: E2E の実行中に、ブラウザから `api-v3.mbta.com` へのリクエストがないことを確かめる
- 地図とグラフの見た目は画像で比べない

### 主なエンティティ（Key Entities）

- 001 の現在値（車両・予測・アラート）と静的データ（路線・駅・路線パターン）を読むだけ。新しいエンティティは作らない

## 成功基準（Success Criteria）*（必須）*

### 測定できる成果（Measurable Outcomes）

（初期値。運用を始めてから見直す）

- **SC-001**: 地図に表示される車両の位置は、収集から 30 秒以内に画面へ反映される（ブラウザの更新間隔 15 秒 + API の応答）
- **SC-002**: 各画面の初回表示が 3 秒以内（Cloud Run のコールドスタートを除く p95）
- **SC-003**: 閲覧者の数が増えても、MBTA API へのリクエスト数は変わらない
- **SC-004**: 主要な 4 画面（地図、駅、アラート、稼働状況）に E2E テストがある

## 前提条件（Assumptions）

- 利用者は少数（自分と許可したユーザー）。画面はデスクトップのブラウザを主に想定し、スマホでも崩れない程度に対応する
- データの鮮度は収集間隔（prod 1 分）に縛られる。ブラウザ側をこれより速く更新しても意味がない
