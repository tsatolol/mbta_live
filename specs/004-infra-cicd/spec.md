# 機能仕様: インフラと CI/CD（Infrastructure & CI/CD）

**feature ブランチ**: `004-infra-cicd`
**作成日**: 2026-11-01
**状態**: 下書き（Draft）
**入力**: Google Cloud に dev と prod の 2 環境を作り、1 つのリポジトリで管理する。dev はレビューなしでデプロイし、prod は承認後にデプロイする。全体で CI は 1 回、CD は 2 回。

## ユーザーシナリオとテスト（User Scenarios & Testing）*（必須）*

### ユーザーストーリー 1 - main に push すると dev に自動で出る（優先度: P1）

開発者として、main に push したら、テストとビルドが 1 回だけ行われ、承認なしで dev 環境に反映されてほしい。

**この優先度の理由**: 変更を実環境ですぐ確かめられ、prod に出す前の確認の場になる。

**単独での確認方法**: main に小さな変更を push し、CI が 1 回動いたあと dev にデプロイされ、dev で collector が 1 回成功することを確認する。

**受け入れシナリオ**:

1. **前提** main への push, **操作** パイプラインが動く, **結果** テスト・ビルド・イメージの push が 1 回だけ行われ、dev のインフラ変更の適用 → DB マイグレーション → デプロイ → 動作確認が承認なしで進む
2. **前提** テストが失敗した, **操作** パイプラインが動く, **結果** dev にも prod にもデプロイされない

---

### ユーザーストーリー 2 - 承認すると同じものが prod に出る（優先度: P1）

リポジトリのオーナーとして、dev で確認できたものを、承認したときにだけ prod に出したい。prod に出るのは dev と同じイメージであってほしい。

**受け入れシナリオ**:

1. **前提** dev へのデプロイが成功した, **操作** オーナーが承認する, **結果** dev と同じイメージ（同じダイジェスト）が prod にデプロイされる。再ビルドはしない
2. **前提** 承認待ちの古い run がある, **操作** それを承認しようとする, **結果** main の最新でないので prod へのデプロイは失敗する
3. **前提** 承認したときに見たインフラの変更内容と、適用直前の変更内容が違う, **操作** prod のデプロイが動く, **結果** インフラの変更は適用されず失敗する

---

### ユーザーストーリー 3 - 問題が起きたら前のイメージに戻す（優先度: P2）

運用者として、prod で問題が起きたら、指定したイメージにすぐ戻したい。

**受け入れシナリオ**:

1. **前提** 戻したいイメージのダイジェスト, **操作** ロールバックを実行し、prod では承認する, **結果** Web とジョブがそのイメージに戻る。インフラ変更とマイグレーションは実行されない

---

### ユーザーストーリー 4 - 環境が分かれていて、許可した人だけが見られる（優先度: P2）

オーナーとして、dev での作業が prod に影響しないようにしたい。画面は許可したユーザーだけが見られるようにしたい。

**受け入れシナリオ**:

1. **前提** dev と prod, **操作** 権限を確認する, **結果** dev 用のデプロイ権限では prod を操作できない
2. **前提** 許可されていない Google アカウント, **操作** 画面を開く, **結果** アクセスが拒否される

### 境界ケース（Edge Cases）

- リポジトリは public。ログや artifact は誰でも見られる
- フォークからの PR では、パイプラインも認証情報も使われない（パイプラインは main への push だけで動く）
- 同時に複数の push があっても、デプロイが途中で中断されない

## 要件（Requirements）*（必須）*

### 機能要件（Functional Requirements）

- **FR-001**: dev と prod は別々の Google Cloud プロジェクトに作らなければならない
- **FR-002**: 両環境のインフラは 1 つのリポジトリの Terraform で管理し、共通のモジュールを使い、違いは変数だけで表さなければならない
- **FR-003**: main への push 1 回につき、CI は 1 回、CD は dev と prod の 2 回だけ実行しなければならない
- **FR-004**: イメージは CI で 1 回だけビルドし、同じダイジェストを dev → prod の順にデプロイしなければならない
- **FR-005**: dev へのデプロイは承認なしで、prod へのデプロイはオーナーの承認後に行わなければならない
- **FR-006**: prod へのデプロイは、main の最新のコミットのときだけ行わなければならない
- **FR-007**: prod のインフラ変更は、承認時に提示した変更内容と一致するときだけ適用しなければならない
- **FR-008**: CI のログと artifact に秘密の値を出してはならない
- **FR-009**: GitHub Actions から Google Cloud への認証は、サービスアカウントのキーを使わずに行わなければならない
- **FR-010**: 指定したイメージに戻すロールバック手段を提供しなければならない（prod では承認が必要）
- **FR-011**: 画面へのアクセスは IAP で許可したユーザーだけに制限しなければならない
- **FR-012**: 環境ごとに予算アラートを設定しなければならない
- **FR-013**: 本番のデータ品質を監視し、異常を通知しなければならない: 最後の収集成功から 3 分以上経過、運行時間中（05:30〜24:00 ET）の車両 0 件、応答の解析に失敗した行の割合が 1% 超、`unknown_stop_ids` の未解決分の増加、前日分の集計の未完了（05:00 ET 時点）

### テスト要件（Testing Requirements）

- **TR-001（インフラのコード）**: CI で `terraform fmt -check` と `validate` を実行し、dev と prod の plan がエラーなく出ることを確かめる
- **TR-002（スモークテスト）**: dev と prod へのデプロイのたびに collector を 1 回実行して成功を確かめる。失敗したらそのデプロイを失敗とする
- **TR-003（マイグレーションの互換性）**: CI で、新しいマイグレーションを適用した DB に対して、prod で動いているコミットの結合テストを実行し、成功することを確かめる（方式は実装時に検証する）
- **TR-004（パイプラインの安全装置）**: main の HEAD でない run の prod デプロイが失敗すること、plan のハッシュが違うときに apply されないことを、実装後に一度ずつ実際に試して確かめる
- **TR-005（監視）**: FR-013 の各監視が、条件を満たしたときに通知されることを dev で一度ずつ確かめる

## 成功基準（Success Criteria）*（必須）*

### 測定できる成果（Measurable Outcomes）

（初期値。運用を始めてから見直す）

- **SC-001**: main への push から dev への反映まで 15 分以内
- **SC-002**: 承認から prod への反映まで 10 分以内
- **SC-003**: ロールバックの実行から完了まで 5 分以内
- **SC-004**: 月額のコストが予算アラートの金額を超えない

## 前提条件（Assumptions）

- GitHub のリポジトリは public なので、GitHub Environments の承認機能（Required reviewers）を無料で使える
- GCP のプロジェクト ID、請求先アカウント、予算額は未定
- PR では CI を動かさない（CI は main への push で 1 回だけ）。push の前にローカルでテストを実行する
