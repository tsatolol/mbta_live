# 機能仕様: インフラと CI/CD（Infrastructure & CI/CD）

**feature ブランチ**: `004-infra-cicd`
**作成日**: 2026-11-01
**状態**: 下書き（Draft）
**入力**: Google Cloud に dev と prod の 2 環境を作り、1 つのリポジトリで管理する。dev はレビューなしでデプロイし、prod は承認後にデプロイする。main の更新 1 回につき、リリース用の CI は 1 回、CD は 2 回。PR の段階では軽いチェックを行い、合格をマージの条件にする。

## ユーザーシナリオとテスト（User Scenarios & Testing）*（必須）*

### ユーザーストーリー 1 - PR の段階で壊れたコードに気づく（優先度: P1）

開発者として、PR を開いた時点で、lint・型・単体テストや秘密の値の混入に問題があれば知りたい。main に入ってから気づくのでは遅いため。

**この優先度の理由**: main に入った変更はそのまま dev にデプロイされる。壊れたものを main に入れないことが、パイプライン全体の前提になる。

**単独での確認方法**: 型エラーを含む PR を開き、チェックが失敗してマージできないことを確認する。

**受け入れシナリオ**:

1. **前提** main 向けの PR, **操作** PR を開く・更新する, **結果** lint・型チェック・単体テスト・秘密の値の検査・依存関係の検査が 5 分以内に終わる
2. **前提** チェックが失敗している PR, **操作** マージしようとする, **結果** マージできない
3. **前提** main, **操作** 直接 push しようとする, **結果** 拒否される

---

### ユーザーストーリー 2 - マージすると dev に自動で出て、実環境で確かめられる（優先度: P1）

開発者として、PR をマージしたら、リリース用のテストとビルドが 1 回だけ行われ、承認なしで dev 環境に反映され、実環境で動くことが確かめられてほしい。

**この優先度の理由**: 変更を実環境ですぐ確かめられ、prod に出す前の確認の場になる。

**単独での確認方法**: 小さな変更をマージし、CI が 1 回動いたあと dev にデプロイされ、スモークテストと dev での E2E が成功することを確認する。

**受け入れシナリオ**:

1. **前提** PR のマージ, **操作** パイプラインが動く, **結果** テスト・セキュリティ検査・ビルド・コンテナの起動確認・イメージの push が 1 回だけ行われ、dev のインフラ変更の適用 → DB マイグレーション → デプロイ → スモークテスト → E2E が承認なしで進む
2. **前提** テストかセキュリティ検査が失敗した, **操作** パイプラインが動く, **結果** dev にも prod にもデプロイされない
3. **前提** dev のスモークテストか E2E が失敗した, **操作** パイプラインが動く, **結果** prod の承認に進まない

---

### ユーザーストーリー 3 - 承認すると同じものが安全に prod に出る（優先度: P1）

リポジトリのオーナーとして、dev で確認できたものを、変更内容を見て承認したときにだけ prod に出したい。prod に出るのは dev と同じイメージで、問題があれば利用者に影響する前に止まってほしい。

**受け入れシナリオ**:

1. **前提** dev のテストが成功した, **操作** 承認画面を見る, **結果** 今回 prod に出るコミットの一覧、追加されるマイグレーション、インフラの変更内容、テスト結果が確認できる
2. **前提** オーナーが承認した, **操作** prod のデプロイが動く, **結果** dev と同じイメージ（同じダイジェスト）が、トラフィック 0% で確認されてから 100% に切り替わる。再ビルドはしない
3. **前提** 新しいリビジョンのスモークテストが失敗した, **操作** prod のデプロイが動く, **結果** トラフィックは切り替わらず、利用者は前のバージョンを使い続ける
4. **前提** 新しいマイグレーションがある, **操作** prod のデプロイが動く, **結果** マイグレーションの前に DB のバックアップが取られる
5. **前提** 承認待ちの古い run がある, **操作** それを承認しようとする, **結果** main の最新でないので prod へのデプロイは失敗する
6. **前提** 承認したときに見たインフラの変更内容と、適用直前の変更内容が違う, **操作** prod のデプロイが動く, **結果** インフラの変更は適用されず失敗する

---

### ユーザーストーリー 4 - 問題が起きたら前のバージョンに戻す（優先度: P2）

運用者として、prod で問題が起きたら、すぐ前のバージョンに戻したい。

**受け入れシナリオ**:

1. **前提** prod で問題が起きた, **操作** ロールバックを実行し、承認する, **結果** web は直前のリビジョン（または指定したイメージ）に、ジョブは指定したイメージに戻る。インフラ変更とマイグレーションは実行されない

---

### ユーザーストーリー 5 - 環境が分かれていて、許可した人だけが見られる（優先度: P2）

オーナーとして、dev での作業が prod に影響しないようにしたい。画面は許可したユーザーだけが見られるようにしたい。

**受け入れシナリオ**:

1. **前提** dev と prod, **操作** 権限を確認する, **結果** dev 用のデプロイ権限では prod を操作できない。prod の認証情報は承認後のジョブでしか使えない
2. **前提** 許可されていない Google アカウントや認証なしのリクエスト, **操作** 画面や API を開く, **結果** アクセスが拒否される

---

### ユーザーストーリー 6 - 本番の異常に気づける（優先度: P2）

運用者として、収集が止まった、データがおかしい、画面がエラーを返している、といった異常を通知で知りたい。

**受け入れシナリオ**:

1. **前提** prod, **操作** 監視の条件（FR-013, FR-020）を満たす, **結果** メールで通知される

### 境界ケース（Edge Cases）

- リポジトリは public。ログや artifact は誰でも見られる
- フォークからの PR では pr-checks だけが動き、GCP の認証情報も Environment の secrets も使われない
- 同時に複数のマージがあっても、デプロイが途中で中断されない
- マイグレーションを適用した後に prod のスモークテストが失敗しても、マイグレーションは後方互換なので前のバージョンはそのまま動く

## 要件（Requirements）*（必須）*

### 機能要件（Functional Requirements）

- **FR-001**: dev と prod は別々の Google Cloud プロジェクトに作らなければならない
- **FR-002**: 両環境のインフラは 1 つのリポジトリの Terraform で管理し、共通のモジュールを使い、違いは変数だけで表さなければならない
- **FR-003**: main の更新 1 回につき、リリース用の CI は 1 回、CD は dev と prod の 2 回だけ実行しなければならない
- **FR-004**: イメージは CI で 1 回だけビルドし、同じダイジェストを dev → prod の順にデプロイしなければならない
- **FR-005**: dev へのデプロイは承認なしで、prod へのデプロイはオーナーの承認後に行わなければならない。prod の承認に進むには、CI と dev のテストがすべて成功していなければならない
- **FR-006**: prod へのデプロイは、main の最新のコミットのときだけ行わなければならない
- **FR-007**: prod のインフラ変更は、承認時に提示した変更内容と一致するときだけ適用しなければならない
- **FR-008**: CI のログと artifact に秘密の値を出してはならない
- **FR-009**: GitHub Actions から Google Cloud への認証は、サービスアカウントのキーを使わずに行わなければならない。prod の認証情報は承認後のジョブでしか使えてはならない
- **FR-010**: 前のバージョンに戻すロールバック手段を提供しなければならない（prod では承認が必要）
- **FR-011**: 画面と API へのアクセスは IAP で許可したユーザーだけに制限しなければならない
- **FR-012**: 環境ごとに予算アラートを設定しなければならない
- **FR-013**: 本番のデータ品質を監視し、異常を通知しなければならない: 最後の収集成功から 3 分以上経過、運行時間中（05:30〜24:00 ET）の車両 0 件、応答の解析に失敗した行の割合が 1% 超、`unknown_stop_ids` の未解決分の増加、前日分の集計の未完了（05:00 ET 時点）
- **FR-014**: main 向けの PR では、lint・型チェック・単体テスト・秘密の値の検査・依存関係の検査を行い、合格をマージの必須条件にしなければならない
- **FR-015**: main は PR 経由の更新だけを受け付けなければならない（直接 push と force push を禁止する）
- **FR-016**: リリース用の CI で、依存関係の脆弱性と秘密の値の混入を検査し、問題があればデプロイしてはならない
- **FR-017**: リリース用の CI で、ビルドしたイメージが起動し、Web とジョブの起動コマンドが動くことを確かめなければならない
- **FR-018**: prod の web は、新しいリビジョンをトラフィック 0% でデプロイしてスモークテストに通ってから、トラフィックを切り替えなければならない。切り替え後のスモークテストに失敗したら、直前のリビジョンに戻さなければならない
- **FR-019**: prod で新しいマイグレーションを適用する前に、DB のバックアップを取らなければならない
- **FR-020**: prod の web の 5xx の割合（5 分間で 5% 超）と応答時間（p95 が 3 秒超）を監視し、通知しなければならない
- **FR-021**: prod の承認画面で、今回出るコミットの一覧、追加されるマイグレーション、インフラの変更内容、テスト結果を確認できなければならない

### テスト要件（Testing Requirements）

- **TR-001（インフラのコード）**: CI で `terraform fmt -check` と `validate` を実行し、dev と prod の plan がエラーなく出ることを確かめる
- **TR-002（スモークテスト）**: dev と prod へのデプロイのたびに、IAP を通して `/api/health` と主要な内部 API が 200 を返し応答のスキーマが正しいこと、認証なしのリクエストが拒否されること、collector の 1 回の実行が成功することを確かめる。HTTP GET の一時的な 500 / 502 / 503 / 504 と接続・タイムアウトだけは、1 回 5 秒・5 秒間隔で最大 3 回まで再試行する（各再試行を記録する）。認証・認可エラー、ほかの HTTP 状態、200 の不正な応答スキーマは再試行しない。再試行の回数制限・対象・待機・タイムアウトを単体テストで確かめる。失敗したらそのデプロイを失敗とする
- **TR-003（マイグレーションの互換性）**: CI で、新しいマイグレーションを適用した DB に対して、prod で動いているコミットの結合テストを実行し、成功することを確かめる（方式は実装時に検証する）
- **TR-004（パイプラインの安全装置）**: main の HEAD でない run の prod デプロイが失敗すること、plan のハッシュが違うときに apply されないこと、タグ付き URL のスモークテストが失敗したときにトラフィックが切り替わらないことを、実装後に一度ずつ実際に試して確かめる
- **TR-005（監視）**: FR-013 と FR-020 の各監視が、条件を満たしたときに通知されることを dev で一度ずつ確かめる
- **TR-006（コンテナの起動確認）**: CI で、テスト用 DB に向けてイメージを起動し、`/api/health` が 200 を返すこと、migrate と collector（フィクスチャ）の起動コマンドが成功することを確かめる
- **TR-007（dev での E2E）**: dev へのデプロイ後、読み取りだけの短い Playwright のテスト（地図に路線と車両が出る、駅の到着表示が出る、アラートの一覧が出る、地図タイルが読み込まれる）を dev の URL に対して実行する
- **TR-008（PR のチェック）**: 型エラー、秘密の値に見える文字列、既知の脆弱性を持つ依存をそれぞれ含む PR を一度ずつ作り、チェックが失敗してマージできないことを実装後に確かめる

## 成功基準（Success Criteria）*（必須）*

### 測定できる成果（Measurable Outcomes）

（初期値。運用を始めてから見直す）

- **SC-001**: PR のチェックは 5 分以内に終わる
- **SC-002**: マージから dev への反映（E2E まで）が 20 分以内
- **SC-003**: 承認から prod への反映まで 15 分以内
- **SC-004**: ロールバックの実行から完了まで 5 分以内
- **SC-005**: 月額のコストが予算アラートの金額を超えない

## 前提条件（Assumptions）

- GitHub のリポジトリは public なので、GitHub Environments の承認機能（Required reviewers）、ブランチ保護、secret scanning、Dependabot alerts を無料で使える
- GCP のプロジェクト ID、請求先アカウント、予算額は未定
- 開発者はオーナー 1 人なので、PR のコードレビュー（承認者）は必須にしない。prod へのリリースの判断はデプロイの承認で行う
- 利用者が少数なので、Canary（トラフィックの段階的な移行）と負荷テストは行わない。ログイン機能・マルチテナント・課金はないので、それらのテストは対象外
