# 機能仕様: 分析（Analytics）

**feature ブランチ**: `003-analytics`
**作成日**: 2026-11-01
**状態**: 下書き（Draft）
**入力**: 蓄積したデータ（001）から運行間隔・予測精度・アラートの傾向を毎日集計し、期間・路線・駅・時間帯で絞り込んでグラフで見られるようにする。

## ユーザーシナリオとテスト（User Scenarios & Testing）*（必須）*

### ユーザーストーリー 1 - 運行間隔の乱れを見る（優先度: P1）

運行を分析する人として、路線・方向・駅ごとに列車の運行間隔がどう推移したか、団子運転や間隔の開きがどれだけ起きたかを見たい。

**この優先度の理由**: 地下鉄の運行品質を表す代表的な指標。

**単独での確認方法**: 到着イベントのフィクスチャから集計ジョブを実行し、運行間隔の画面に推移・分布・団子運転と間隔の開きの件数が表示されることを確認する。

**受け入れシナリオ**:

1. **前提** 集計済みのデータ, **操作** 路線・方向・駅・期間を選ぶ, **結果** 運行間隔の推移グラフと分布、団子運転と間隔の開きの件数が表示される
2. **前提** Green Line の幹線区間の駅, **操作** 路線に `Green`（全支線合算）を選ぶ, **結果** 支線をまとめた運行間隔が表示される
3. **前提** 今日の分（まだ集計されていない）, **操作** 期間に今日を含める, **結果** 今日の分も生データから計算して表示される

---

### ユーザーストーリー 2 - 到着予測の精度を見る（優先度: P1）

分析する人として、到着予測が実際の到着とどれだけずれていたかを、到着の何分前の予測か（リード時間）、予測の種類、路線ごとに見たい。

**受け入れシナリオ**:

1. **前提** 集計済みのデータ, **操作** 予測精度の画面を開く, **結果** リード時間ごとの誤差の分布、平均誤差、平均絶対誤差、p90、±60 秒以内の割合が表示される
2. **前提** 予測精度の画面, **操作** 予測の種類（`MID_TRIP` / `AT_TERMINAL` / `REVERSE_TRIP`）で絞る, **結果** その種類だけの精度が表示される
3. **前提** 補間で推定した到着, **操作** 精度を集計する, **結果** 集計に含めない

---

### ユーザーストーリー 3 - アラートの傾向を見る（優先度: P2）

分析する人として、路線・影響の種類・原因ごとに、アラートがどれだけ出て、どれだけ続いたかの推移を見たい。

**受け入れシナリオ**:

1. **前提** 集計済みのデータ, **操作** アラートの傾向の画面を開く, **結果** 路線別・effect 別・cause 別の件数と継続時間の推移が表示される
2. **前提** 遅延系（`DELAY`, `SUSPENSION`, `SHUTTLE`, `STATION_CLOSURE`）とお知らせ系（`NOTICE`, `STATION_ISSUE` など）, **操作** 画面を見る, **結果** 両者は分けて表示される
3. **前提** まだ始まっていない予告だけのアラート, **操作** 集計する, **結果** 件数に含めない

---

### ユーザーストーリー 4 - 曜日と時間帯のパターンを見る（優先度: P2）

分析する人として、曜日 × 時間帯のヒートマップで、運行間隔・予測誤差・アラートが起きやすい時間帯を見たい。

**受け入れシナリオ**:

1. **前提** 集計済みのデータ, **操作** パターンの画面を開く, **結果** 曜日 × 時間帯（ボストン時間）のヒートマップが表示され、指標（運行間隔 p90、予測誤差、アラートの分数）を切り替えられる

### 境界ケース（Edge Cases）

- 運休時間帯をまたぐ間隔（60 分超）は運行間隔に含めない
- 夏時間の切り替え日は 1 日が 23 / 25 時間になる
- 集計の定義を変えた場合、生データが残っている期間（prod 28 日 / dev 3 日）しか再集計できない
- 到着時刻の推定精度は ±60 秒程度（dev はさらに低い）。画面にこの注記を出す

## 要件（Requirements）*（必須）*

### 機能要件（Functional Requirements）

- **FR-001**: システムは、毎日、前の運行日の運行間隔・予測精度・アラートを集計して保存しなければならない。集計結果は無期限に残す
- **FR-002**: システムは、集計に成功した運行日を記録し、001 が生データを削除してよいかを判断できるようにしなければならない
- **FR-003**: システムは、指定した期間について集計を再実行できなければならない（生データが残っている範囲）
- **FR-004**: システムは、運行間隔・予測精度・アラートの傾向・曜日 × 時間帯のパターンの 4 つの画面を提供しなければならない
- **FR-005**: 各画面は、路線・方向・駅・期間で絞り込めなければならない（指標に関係するものだけ）
- **FR-006**: 当日の分は、集計テーブルではなく生データから計算して表示しなければならない
- **FR-007**: 指標の定義（data-model.md）としきい値は、コードの一か所（`src/lib/metrics/constants.ts`）で調整できなければならない
- **FR-008**: 分析の画面には、到着時刻の推定精度（±60 秒程度）の注記を出さなければならない

### テスト要件（Testing Requirements）

- **TR-001（指標の定義）**: 運行間隔（60 分超の除外、団子運転、間隔の開き）、予測誤差（符号、`interpolated` の除外、バケットと種類での分割）、アラート（UPCOMING の除外、日をまたぐ継続時間）の TypeScript 版を、入力と期待値の表で単体テストする
- **TR-002（SQL と TypeScript の一致）**: 同じ小さなデータを本物の PostgreSQL に入れ、集計 SQL（TypedSQL）の結果が TypeScript 版と一致することを確かめる
- **TR-003（境界）**: Green Line 幹線の合算、運行日の日付またぎ、夏時間の切り替え日（23 / 25 時間の日）、データが 0 件の日を確かめる
- **TR-004（再集計）**: 同じ期間を 2 回集計しても結果が変わらないこと、`aggregate_runs` が更新されること、当日分を生データから計算した値と翌日の集計結果が一致することを確かめる
- **TR-005（内部 API と画面）**: 分析 API の結合テスト（応答のスキーマ、`definitionVersions`）と、4 つの画面が表示される E2E を書く。グラフは画像で比べず、グラフに渡すデータへの変換を単体テストする

### 主なエンティティ（Key Entities）

- **日次の運行間隔統計**: 運行日 × 路線 × 方向 × 駅 × 時間帯
- **日次の予測精度**: 運行日 × 路線 × 方向 × リード時間 × 予測の種類 × 時間帯
- **日次のアラート統計**: 運行日 × 路線 × effect × cause
- **集計の実行記録**: 運行日ごとの成否

## 成功基準（Success Criteria）*（必須）*

### 測定できる成果（Measurable Outcomes）

（初期値。運用を始めてから見直す）

- **SC-001**: 日次集計は毎日 05:00 ET までに前の運行日の分を完了する
- **SC-002**: 28 日分の範囲を指定しても、各分析画面が 3 秒以内に表示される（コールドスタートを除く p95）
- **SC-003**: 指標の計算関数はすべて単体テストで境界ケース（日付またぎ、Green 幹線の合算、補間の除外）を確認している

## 前提条件（Assumptions）

- 団子運転・間隔の開きのしきい値は初期値で始め、実データを見て調整する
- 時刻表（`/schedules`）との比較による遅延指標は、この feature の範囲外（将来の改善）。便 ID の多くが時刻表にない（`ADDED-…` / `NONREV-…`）ので、比べるなら便単位ではなく運行間隔で比べる必要がある
