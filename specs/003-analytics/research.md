# 調査と決定: 分析

## 集計のタイミング

- **決定**: aggregate ジョブを毎日 04:30 ET に実行し、前の運行日を集計する。同じジョブで 001 のパーティションの作成と削除も行う
- **理由**: 運行日は ET の 03:00 に切り替わる（運行日 = ET の時刻 − 3 時間）。sync-static（04:00 ET）の後に動かす

## 当日のデータ

- **決定**: 当日の分は API のリクエスト時に生データから計算する
- **理由**: 集計は 1 日 1 回なので、当日の状況を見るには生データを使うしかない。1 日分なら計算量は小さい

## 間隔の開き（gap）の基準

- **決定**: 過去 28 日の中央値を、生データではなく `daily_headway_stats.p50_sec` から求める
- **理由**: 生データの保持期間（prod 28 日 / dev 3 日）に左右されないようにするため

## 補間した到着の扱い

- **決定**: `source = interpolated` の到着イベントは予測精度の集計から除く。運行間隔には含める
- **理由**: 補間は予測精度の評価には粗すぎる。運行間隔は到着イベントが欠けるほうが歪みが大きい

## 予測の種類での分割

- **決定**: 予測精度を `update_type`（`MID_TRIP` / `AT_TERMINAL` / `REVERSE_TRIP`）ごとにも集計する
- **理由**: 実測で、API が示す不確かさが種類ごとに 60 / 120 / 360 秒と大きく違った。まとめて集計すると精度の違いが見えなくなる

## グラフ: Apache ECharts

- **決定**: Apache ECharts
- **理由**: ヒートマップと大量の時系列を扱いやすい。仮の選定で、変更してよい

## 集計クエリ: `$queryRaw` + zod（TypedSQL は使わない）

- **決定**: `percentile_cont` やウィンドウ関数を使う集計は、Prisma の `$queryRaw`（`Prisma.sql` のタグ付きテンプレート）で書き、結果の行を zod で検証する。SQL は `src/lib/db/analytics-sql.ts` に集める
- **理由**: Prisma のクエリ API では表現できない（`specs/001-data-collection/research.md`）。TypedSQL（`prisma generate --sql`）は生成のときに DB への接続が必要で、イメージのビルド（Dockerfile）と PR のチェックには DB がない。生成物をコミットする運用にすると、SQL と生成物のずれを別に点検する必要が出る。`$queryRaw` + zod なら、型は zod のスキーマから得られ、本物の PostgreSQL での結合テスト（TR-002）で SQL を確かめられる
- 当初の計画は TypedSQL（`prisma/sql/*.sql`）だった。plan.md と data-model.md も合わせて直した（2026-11-04）

## 1 つの SQL を、日次集計と当日の計算の両方に使う

- **決定**: 指標ごとに「運行日を 1 つ受け取り、集計の行を返す SELECT」を 1 つだけ持つ。aggregate ジョブはその結果を集計テーブルに INSERT し、分析 API は当日の分を同じ SELECT で計算する
- **理由**: 当日分を生データから計算した値と、翌日の集計結果が一致すること（TR-004）を、定義を 2 つ持たずに保証するため

## 曜日種別（間隔の開きの基準）

- **決定**: 運行日の曜日で `weekday`（月〜金）/ `saturday` / `sunday` に分ける。祝日は考えない（MBTA は祝日に土曜・日曜のダイヤで走ることがあるが、祝日の一覧を持たないため）。`src/lib/time.ts` の `dayTypeOf(serviceDate)`
- 基準の中央値は、対象の運行日より前の 28 日の、同じ (路線, 方向, 駅, 曜日種別, 時間帯) の `p50_sec` の中央値。基準がない（集計の履歴がない）ときは、間隔の開きを数えない（0 件）。画面には、基準がない日があることが分かるよう `gapBaselineMissing` を返す

## 時間帯（hour）

- **決定**: 運行間隔は後の到着の時刻、予測精度は実際の到着の時刻、アラートはその分数が含まれる時刻を、ET の時（0〜23）にする。夏時間が終わる日の 1 時台（2 回ある）は 1 つにまとめる
- 運行日は ET の 03:00 に始まるので、1 日の時間帯は 3, 4, …, 23, 0, 1, 2 の順になる。画面もこの順に並べる

## Green Line の合算

- **決定**: `route_id = Green` の運行間隔は、Green の 2 つ以上の支線が通る親駅（路線パターンの `station_ids` から求める）で、支線を区別せずに (方向, 駅) ごとに到着を並べて計算する。方向 ID は 4 支線で同じ（0 = 西行き、1 = 東行き）
- 支線が 1 つだけの駅では `Green` を作らない（支線別の値と同じになるため）

## 曜日 × 時間帯のヒートマップ

- **決定**: ヒートマップのセルは日次の集計から作る。`headway_p90` と `prediction_abs_error` は、そのセルに入る (運行日, 時間帯) の値を件数 `n` で重み付けした平均にする（日をまたいだ正確なパーセンタイルではない。画面に注記する）。`alert_minutes` は、そのセルの時間帯にアラートが有効だった分数の、日あたりの平均
- アラートの分数を時間帯ごとに出すため、`hourly_alert_minutes`（運行日 × 路線 × 時間帯 × 区分）を足した。`daily_alert_stats` には時間帯がないため

## 集計の冪等性

- **決定**: 1 つの運行日の集計は、1 つのトランザクションで「その運行日の行を消す → 入れ直す → `aggregate_runs` を upsert する」。同じ運行日を何度集計しても結果は同じ（TR-004）
- 集計の範囲（`--from` / `--to`）は古い順に 1 日ずつ処理する。間隔の開きの基準が、前の日の集計結果を使うため

## 指標がそろうまで生データを消さない

- **決定**: 定義の版 `AGGREGATE_DEFINITION_VERSION` は、3 つの指標（運行間隔・予測精度・アラート）の集計がそろうまで 0 にする。001 の生データの削除は、版が `MIN_DROPPABLE_DEFINITION_VERSION`（1）以上で成功した運行日だけを対象にする
- **理由**: 集計の骨組み（フェーズ 2）だけを prod に出すと、指標を計算していないのに `aggregate_runs` が success になり、保持期間を過ぎた生データが消えてしまう。後から指標を足しても、その期間は集計できなくなる

## フェーズ 1〜2 の実装で決めたこと（2026-11-04）

- **依存**: Apache ECharts 6.1.0。`echarts/core` に、使うグラフ（折れ線・棒・ヒートマップ）と部品だけを登録する（`src/components/charts/echart.tsx`）。E2E はグラフの見た目ではなく、`window.__mbtaCharts[id].getOption()` で渡したデータを確かめる（002 の地図と同じ考え方）
- **集計ジョブ**: 運行日ごとの集計に失敗しても、ほかの運行日は続けて集計し、最後にジョブを失敗にする。失敗した運行日は `aggregate_runs` に `failed` を記録する（前に成功していても上書きする。集計テーブルの行はトランザクションが戻るので前回のまま）。今日以降の運行日は集計できない（`--to` は昨日まで）。一度に 92 日まで。1 日の集計のトランザクションのタイムアウトは 5 分
- **絞り込みの状態**: 分析の画面の絞り込み（期間・路線・方向など）は URL のクエリに持つ。リンクで共有でき、タブを移っても期間と路線を引き継ぐ
- **期間の既定**: 今日を含む直近 7 日。最大 92 日。今日より後は指定できない
- **テスト用データ**: 決まった規則で作る（`tests/helpers/analytics-seed.ts`）。1 日に到着 約 1,500 件・予測 約 7,600 件あり、Prisma の `createMany` では 1 日 2 秒以上かかったので、`jsonb_to_recordset` の 1 本の SQL で入れる（8 日分で 1 秒程度）。E2E では `analytics` シナリオのときだけ入れる（ほかの E2E を遅くしないため）
