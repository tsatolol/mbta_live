# 調査と決定: 画面デザインの刷新（Platform）

## 方向性

- **決定**: ボストン地下鉄の駅の案内に根ざす（「Platform」）。路線色の帯、路線図の形、ホームの発車標（濃い板に琥珀色の文字）を手がかりにする。2026-11-05 に承認
- **理由**: いまの見た目は汎用のテンプレートのままで、題材（地下鉄の運行の監視）が見た目から分からない。題材の世界にある形を使うと、説明なしで読み方が伝わる（帯の色 = 路線、板の数字 = あと何分）
- **大胆にするのは 1 か所**: 到着表示の板。ほかは静かにする

### よくある既定の見た目との突き合わせ（計画の見直し）

最初の案を、どの題材にも出てくる既定の見た目と突き合わせて、次を変えた。

| 最初の案                                    | 問題                                         | 変えたもの                                                                         |
| ------------------------------------------- | -------------------------------------------- | ---------------------------------------------------------------------------------- |
| 到着表示にドットマトリクスの LED 風の書体   | 目新しさのための書体で読みにくい。飾りになる | 本文と同じ Overpass の等幅の数字を、琥珀色で大きく                                 |
| 分析の画面の上に、大きな数字のタイルを 4 つ | 「大きな数字 + 小さなラベル」は既定の見た目  | 要点を一文で書き、数字は文の中に入れる                                             |
| ページ全体を暗くして、強調の色を 1 つ       | 「黒い背景 + 1 つの強い色」は既定の見た目    | 濃いのは到着表示の板だけ（実物の発車標に合わせる）。ページは駅のコンクリートの灰色 |

### 分かったこと

- **いまの Orange Line のボタンは基準を満たしていない**: 白い文字と `#ED8B00` は 2.53:1。帯の上の文字は `--ink`（5.80:1）にする
- **路線色を文字に使うと、明るい表示でも基準に届かないものがある**: Red `#DA291C` は `--surface` に対して 4.45、Green `#00843D` は 4.40。路線色は帯・線・点だけに使い、文字には使わない
- **暗い表示では MBTA の路線色の多くが見えにくい**: Blue `#003DA5` は暗い `--panel` に対して 1.68、Red 3.29、Green 3.33。同じ色相で明るくした値（Red `#F0564A` 4.67、Green `#2FB46A` 5.99、Blue `#5B8DEF` 4.95）にする。Orange は 6.32 でそのまま使える
- **暗い表示で帯の上に文字を載せるとき**は、白ではなく暗い背景の色（`#10181D`）にする（白は 2.67〜3.42 で足りない。暗い文字は 5.24〜7.09）
- **グラフ**: 003 の配色（明るい表示 `#2A78D6` / `#EB6834`）は、白い背景で dataviz の検証をすべて通している。暗い表示の値（`#3987E5` / `#D95926`）も、暗い `--panel`（`#18232A`）に対して検証をすべて通した

### 重要度の表し方

- **決定**: 遅延系のアラートとデータが古いときは、`--ink` と `--panel` の 2 色の斜めの縞（工事現場や踏切の警戒の帯）+ 警告のアイコン + 文言。お知らせ系は縞なし + 情報のアイコン
- **理由**: 路線の赤・橙と、重要度の赤・黄が混ざると、どちらの意味か分からなくなる。縞は色を見分けられなくても、Windows のハイコントラスト（forced-colors）や白黒の印刷でも残る

## 書体

- **決定**: Overpass（可変フォント、OFL）。`@fontsource-variable/overpass` 5.3.0（2026-07-19 公開）から、latin と latin-ext のサブセットを自前で配信する
- **理由**: Overpass は米国の道路標識の書体（Highway Gothic）の系譜で、案内の文字としての読みやすさと題材の雰囲気がある。可変フォント 1 つで 400〜800 の太さをまかなえる
- **等幅の数字を確かめた**: ブラウザで描いて幅を測った（太さ 700、100px）。比例の数字では「1111」が 160.0px・「0000」が 264.1px、`font-variant-numeric: tabular-nums` では両方 246.4px。毎秒変わる残り時間の幅が揺れない
- **配り方**: `next/font/google` はビルドのときに Google Fonts から取得する（ビルドの環境にネットワークが要る）。`@fontsource-variable` は npm のパッケージに書体のファイルが入っているので、ビルドでも閲覧でも外部に通信しない（FR-013）。イメージに同梱される（憲章 VI）
- **読み込み**: `font-display: swap`。latin のファイル（約 40KB）だけを `preload` する。代わりの書体（`system-ui`）との寸法の差で画面がずれないよう、`size-adjust` を合わせる（実装で確かめる）

## 暗い表示と切り替え

- **決定**: 表示の選択は「明るい」「暗い」「OS に合わせる（既定）」の 3 つ。localStorage の `mbta-live:theme` に残す。`html` に `data-theme="light"` / `"dark"` を付け、「OS に合わせる」では付けない。CSS は次の 3 つでトークンの値を入れ替える:
  - `:root`（明るい表示の値）
  - `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { … } }`（OS が暗い表示で、明るい表示を選んでいない）
  - `:root[data-theme="dark"] { … }`（暗い表示を選んだ）
- **一瞬違う表示が出ないように**: ルートの layout の `<head>` に、localStorage を読んで `data-theme` を付けるだけの小さなインラインのスクリプトを置く（React が動く前、最初の描画の前に動く）。読めない・値が不正なら何もしない（OS に合わせる）。`<html suppressHydrationWarning>` にする（サーバーの HTML と属性が違うため）
- **切り替えの部品**: 3 つのボタンの組（`role="radiogroup"`、各ボタンは `role="radio"` と `aria-checked`、アイコン + 見えるラベルかツールチップ）。スマホではメニューの中に置く
- **Tailwind の `dark:` は使わない**: いまの `@custom-variant dark (&:is(.dark *))` は使われていない。部品はトークンだけを参照し、値が入れ替わる
- **JavaScript で見た目を決める部品**（地図・グラフ）は、解決した表示（明るい / 暗い）をフック（`useResolvedTheme`）で受け取り、変わったら描き直す。フックは `data-theme` の変化と `matchMedia` の変化の両方を見る

## 地図

- **暗い表示の地図**: OpenFreeMap の `https://tiles.openfreemap.org/styles/dark`（Dark Matter の fork）を使う。明るい表示は今の `positron`。OpenFreeMap の README によると、Dark は上流のまま手を入れていない（書体だけ Noto Sans）。見た目は実装で確かめ、路線と列車の印が埋もれないかを見る
- **スタイルの切り替え**: MapLibre の `setStyle` はソースとレイヤーを消すので、スタイルの読み込みのあとに路線・列車のソースとレイヤーを足し直す（今の初期化の処理を関数にまとめて使い回す）
- **路線と列車の印**: 路線の線を太く（今の 3px → 5px）、列車の矢印を大きく（1.3 倍）、印の周りに `--panel` の色の縁を付けて、線の上でも見えるようにする
- **凡例**: 路線ごとの列車の数は、今の車両の応答から画面で数える（`src/lib/display/line-counts.ts`）。凡例の行は切り替えのボタン（`aria-pressed`）で、選んでいない路線は帯を中抜きにし、文字を `--ink-muted` にする（色以外でも分かる）
- **地図の高さ**: 画面の高さ（`100dvh`）からヘッダーとフッターの 1 行を引いた高さ。スマホでは凡例を地図の下に閉じた帯（「Lines」と合計の列車の数）で出し、押すと開く

## 到着表示

- **残り時間の表し方を 1 つに**: 残り 2 分以上は「n min」、2 分未満は「1:23」（分:秒）、到着の直前（0 秒以下になったら次の取得まで）は「Now」。1 つの便には常に 1 つの表し方。いまの「6:27」と「6 min」の重複をなくす（FR-006）
- **毎秒のカウントダウン（002 FR-004）**: 2 分未満の便は秒が毎秒減る。2 分以上の便も、毎秒の時刻で計算し直し、分の境目で表示が変わる
- **板の行**: 路線色の帯（左端、6px）、行先（`--text-lg`、800）、路線と方向（`--board-muted`、例「Red Line, southbound」）、次の 3 本の残り時間（`--countdown`、`--text-2xl`）と、その下に到着時刻（`--board-muted`、`--text-xs`）。始発駅は時刻に「departs」を添える。運休は時刻に取り消し線と「Cancelled」（`--board-ink`）

## 駅の一覧（路線図）

- **入力**: 今の `GET /api/static/stops` は、Red の Ashmont と Braintree の並びを 1 つにつないで返す（002 の research.md）ので、分岐の位置が分からない。応答に路線パターンごとの駅の並び（`patterns`）を足す（後方互換）
- **組み立て**: 路線ごと（Green は 4 支線をまとめて 1 つ）に、方向 0 の canonical な路線パターンの駅の並びから、駅ごとに「その駅を通るパターンの組」を求め、同じ組が続く駅を 1 つの区間にまとめる。区間をパターンの並びの順につなぎ、組が分かれるところ（分岐）では、分かれた先の区間を横に並べる列として描く（`src/lib/display/strip-map.ts`。純粋関数で単体テストする）
- **駅の数**: Green の 4 支線をまとめると 70 駅（Red 22、Orange 20、Blue 12、Mattapan 8）。縦に 1 列で並べると、いまより長くなるので、分岐を横に並べる。Green は幹線（Lechmere〜Kenmore）と、北の端（Medford/Tufts と Union Square）、西の 4 支線（B・C・D と、Copley で分かれる E）に分かれ、縦は 35 行ほどになる見込み
- **配置**: デスクトップでは路線を列に並べる（Red の下で Mattapan・Blue を横に並べた列、Orange の列、Green の幅の広い列）。スマホでは路線を縦に並べ、分岐の列は横に並べたまま（はみ出すときは区間ごとに折り返す）
- **検索**: 該当する駅を `--ink` の太字と点の拡大で強調し、該当しない駅は `--ink-muted` にする（隠さない。路線の形を保つため）
- **高さの目標（SC-003）**: 1 行 24px で、デスクトップで 1,350px 以下。実装で測る

## アラート・稼働状況・分析

- **アラート**: カードをやめ、細い線で区切った一覧にする。遅延系は左に縞の帯 + 警告のアイコン + 「Disruption」、お知らせ系は情報のアイコン + 「Notice」。路線は小さな帯（路線色）+ 名前
- **稼働状況**: 上に状態の一文（例「Collection is running normally. The last successful run was 12 s ago.」「Collection is running, with 3 failures in the last 24 hours.」）とチェック / 警告のアイコン。表はその下。API が持つ24時間の失敗件数を使う
- **分析**: 上に要点の文（`src/lib/display/summaries.ts`。運行間隔の代表値は typical headway of approximately と表記する）。文の中の数字に、今の `stat-…-value` の `data-testid` を付ける。グラフは枠に入れず、見出しと余白で区切る

## アイコン

- **決定**: 使うアイコン（警告の三角、情報の丸、チェック、太陽、月、画面、メニュー、閉じる）は、インラインの SVG の部品として持つ（`src/components/icons.tsx`）。アイコンのライブラリは足さない

## フェーズ 1〜2 の実装で決めたこと（2026-11-05）

- **書体の読み込み**: fontsource の CSS をそのまま読み込むのではなく、同じパッケージの latin のファイル（`overpass-latin-wght-normal.woff2`）を `next/font/local` で読み込むことにした。`next/font` が preload と、代わりの書体（Arial）の寸法の調整（`size-adjust` など）を自動でする。latin だけにした（駅名・アラートは英語。latin にない文字は代わりの書体で出る）。ブラウザで、Overpass が読み込まれ、`body` の書体になることを確かめた
- **グラフの色**: グラフを組み立てる関数は、色を CSS 変数の参照（`"var(--chart-1)"` など）で書き、グラフの部品（`echart.tsx`）が描く直前にいまの表示の値に置き換える（`resolve-css-vars.ts`）。表示が変わったら描き直す。値の正を CSS（= 契約）の 1 か所に保ち、グラフの関数に表示を渡して回らずに済む。グラフが参照する変数が明るい・暗いの両方で定義されていることを単体テストで確かめる
- **グラフの書体**: ECharts は canvas に描くので、CSS の書体を継げない（`fontFamily: "inherit"` は効かず、ブラウザの既定の書体になっていた）。描く直前に `body` の書体の名前を渡す
- **グラフの軸と凡例の文字**: 11px → 13px（文字の大きさの段階の最小）。軸の文字は `--ink-muted`（明るい 5.80:1、暗い 6.41:1）。`#898781` は白い背景で 3.5:1 で、小さな文字には足りなかった。軸の線は `--chart-axis`（飾り）
- **ヒートマップの暗い表示**: 暗い背景では、小さい値が背景に沈み、大きい値ほど明るくなるよう、同じ青の段階を逆順に使う（`#104281` → `#CDE2FB`）
- **既存の部品**: shadcn 由来の名前（`--background`、`--muted-foreground` など）は新しいトークンに対応させて残し、各ストーリーで部品を作り直すときに新しい名前に移す。影はなくした。入力欄の独自のフォーカスの輪（1px）をやめ、共通のフォーカスの輪（2px + 2px の隙間）にした。`--warning` は、ユーザーストーリー 1 で縞の帯に置き換えるまで残す
- **axe の検査の仕組み**: 作り直す前の画面で試した。稼働状況と運行間隔の画面は、明るい・暗いとも違反 0。到着表示は color-contrast の違反が 20（路線色の見出しの上の白い文字など）で、ユーザーストーリー 3 で作り直す

## フェーズ 3（US1 共通の土台）の実装で決めたこと（2026-11-05）

- **ヘッダー**: 高さ 56px の 1 行。デスクトップは「名前・DEV のバッジ・画面の切り替え・鮮度・表示の切り替え」。幅 768px 未満は「名前・DEV・鮮度（短い形）・メニュー」で、画面の切り替えと表示の切り替えはメニューに入れる。390px で 1 行・56px（SC-001 の 64px 以下）
- **今の画面の示し方**: 太字 + 下の 3px の帯（色以外でも分かる）
- **DEV のバッジ**: 琥珀（強調の色は到着表示だけ。FR-002）をやめ、`--ink` の枠線のバッジにした
- **鮮度**: 「Updated 12 s ago」を毎秒更新。正常は塗りつぶした点、古いときは警告のアイコン（色だけで区別しない）。押すと正確な時刻（ボストン時間）が出る。スマホは短い形（「12 s」）。E2E では、見えている文字だけを比べる（`useInnerText`。デスクトップ用とスマホ用の両方の文字が DOM にあるため）
- **データが古いときの帯**: 縞の帯を文言のすぐ左（本文の幅の中）に置いた。最初は画面の左端に置いたが、デスクトップで文言から離れて見えた。文言は「Live data is stale: the last successful collection was 4 min ago, at 10:15 AM ET.」（どれくらい古いかと時刻）
- **表示の切り替え**: 3 つのラジオボタン（WAI-ARIA の radio group。矢印キーで移り、選んだものだけが Tab で止まる）。選んでいるものだけ名前（「Dark」など）も出す。ヘッダーとメニューの両方に置くので、`data-testid` の頭を分けた（`theme-*` / `menu-theme-*`）
- **最初の描画の確かめ方**: E2E で、`DOMContentLoaded`（React が動く前）の `data-theme` と背景色を記録して、選んだ表示になっていることを確かめた
- **axe**: 稼働状況の画面（共通のヘッダーとフッターを含む）を、明るい表示・暗い表示・スマホのメニューを開いた状態で検査し、違反 0

## フェーズ 4（US2 地図）の実装・検証（2026-11-06）

- **整合性の点検**: US2 のシナリオ 4 だけが「凡例は地図の上」となっていた。plan・tasks・この文書の決定に合わせ、spec を「地図の下に折りたたまれた帯」に修正した。仕様を先に修正してから実装した。リポジトリには Spec Kit のコマンド実装が未導入のため、憲章・spec・plan・契約・tasks と既存のコードを直接突き合わせた。
