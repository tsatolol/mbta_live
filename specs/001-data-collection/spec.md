# 機能仕様: データ収集（Data Collection）

**feature ブランチ**: `001-data-collection`
**作成日**: 2026-11-01
**状態**: 下書き（Draft）
**入力**: MBTA V3 API から地下鉄（Rapid Transit）の車両位置・到着予測・運行アラートを定期的に取得し、リアルタイム表示と分析に使えるように蓄積する。

## ユーザーシナリオとテスト（User Scenarios & Testing）*（必須）*

### ユーザーストーリー 1 - 最新の運行状況が常に DB にある（優先度: P1）

運行監視をする人として、誰も画面を開いていない時間も含めて、全路線の車両位置・到着予測・運行アラートの最新の状態が一定間隔で保存されていてほしい。そうすれば、画面を開いたときにすぐ最新の状況が分かり、後から振り返ることもできる。

**この優先度の理由**: リアルタイム画面（002）と分析（003）のどちらもこのデータがないと成り立たない。分析には過去のデータが必要なので、最初に動かし始める必要がある。

**単独での確認方法**: 収集ジョブを 1 回実行し、現在値テーブルに対象 8 路線の車両・予測・アラートが入ること、`collector_runs` に成功が記録されることを確認する。

**受け入れシナリオ**:

1. **前提** 運行時間中, **操作** 収集ジョブが実行される, **結果** 運行中の車両・予測・アラートが現在値テーブルに入れ替わり、実行結果（件数、レート制限の残量）が記録される
2. **前提** 運行時間外（車両も予測も 0 件）, **操作** 収集ジョブが実行される, **結果** 現在値テーブルは空になり、ジョブは成功として記録される
3. **前提** MBTA API が 429 を返す, **操作** 収集ジョブが実行される, **結果** リトライせずに終了し、失敗として記録される。次の回は通常どおり動く
4. **前提** 前の回のジョブがまだ動いている, **操作** 次の回が起動する, **結果** 次の回はすぐに終了し、データは二重に書き込まれない

---

### ユーザーストーリー 2 - 実際の到着時刻が記録される（優先度: P1）

分析をする人として、各列車が各駅に実際に到着した時刻を記録しておいてほしい。運行間隔と予測精度の計算に使うため。

**この優先度の理由**: MBTA API は実際の到着時刻を返さないので、収集のたびに車両の動きから推定して残さないと後から作れない。

**単独での確認方法**: 記録済みの 2 回分の車両・予測のフィクスチャを順に入力し、期待どおりの到着イベントが作られることを単体テストで確認する。

**受け入れシナリオ**:

1. **前提** 車両が駅 S に停車中（`STOPPED_AT`）, **操作** 収集する, **結果** その便の駅 S への到着イベントが 1 件だけ作られる
2. **前提** 前回から今回の間に車両が複数の駅を通過した, **操作** 収集する, **結果** 通過した駅にも到着イベントが作られ、推定方法（`predicted_last` / `interpolated`）が記録される
3. **前提** 位置情報が 3 分以上更新されていない車両, **操作** 収集する, **結果** その車両からは到着イベントを作らない

---

### ユーザーストーリー 3 - 予測の記録が分析できる量に抑えられている（優先度: P2）

分析をする人として、到着予測が到着の何分前にどう出ていたかを記録しておいてほしい。ただし DB の容量を圧迫しない量で。

**この優先度の理由**: 予測精度の分析（003）に必要。全件を毎回保存すると容量が足りなくなる。

**単独での確認方法**: 同じ便・駅の予測を、到着の 16 分前から 0 分前まで 1 分ごとに入力し、リード時間のバケットごとに 1 件だけ保存されることを確認する。

**受け入れシナリオ**:

1. **前提** ある便・駅の予測が毎回取得される, **操作** 収集を続ける, **結果** リード時間のバケット（1, 3, 5, 10, 15 分）ごとに最初の 1 件だけが保存される
2. **前提** 運休（`CANCELLED`）・通過（`SKIPPED`）・始発駅（到着予定時刻なし）の予測, **操作** 収集する, **結果** これらは保存しない

---

### ユーザーストーリー 4 - 駅と路線の情報が毎日更新される（優先度: P2）

画面と分析で使う路線・駅・路線形状の情報を、毎日 MBTA から取り込んでおいてほしい。駅名や路線色をコードに直接書かずに済むように。

**単独での確認方法**: 静的データの同期ジョブを実行し、8 路線、親駅 125 件、ホーム（終点駅の番線を含む）、通常運行の路線パターン 18 件が保存されることを確認する。

**受け入れシナリオ**:

1. **前提** 同期ジョブが実行される, **操作** 完了する, **結果** 路線・駅（親駅とホーム）・路線パターン（停車順と形状）が upsert される
2. **前提** 収集ジョブが駅一覧にない ID を見つけた, **操作** 次の同期ジョブが実行される, **結果** その ID の駅を MBTA から取得して追加する

---

### ユーザーストーリー 5 - 古い生データは自動で消え、集計前のデータは消えない（優先度: P3）

運用者として、生データは保持期間を過ぎたら自動で削除されてほしい。ただし、まだ集計されていない日のデータは消えないでほしい。

**受け入れシナリオ**:

1. **前提** 保持期間（prod 28 日 / dev 3 日）を過ぎ、集計が済んだ運行日の生データ, **操作** 日次ジョブが実行される, **結果** その日のデータが削除される
2. **前提** 保持期間を過ぎたが、集計が失敗していて済んでいない運行日, **操作** 日次ジョブが実行される, **結果** その日のデータは削除されない

### 境界ケース（Edge Cases）

- 運行日は日付をまたぐ（深夜 0〜3 時の列車は前日の運行日に属する）。夏時間の切り替え日も正しく扱う
- 車両の `stop` が `null`、`updated_at` が数十分前のまま、という車両がある
- 駅 ID に、駅一覧の通常の取得方法では返らない終点駅の番線（`Alewife-01` など）が出てくる
- 路線パターンに臨時の代行バス路線（`Shuttle-*`）が混ざる
- 便 ID の多くが時刻表にない ID（`ADDED-…` / `NONREV-…`）
- アラートのフィードには、まだ始まっていない予告（`UPCOMING`）も含まれる
- MBTA の応答の一部の行がスキーマに合わない

## 要件（Requirements）*（必須）*

### 機能要件（Functional Requirements）

- **FR-001**: システムは、対象 8 路線（Red, Mattapan, Orange, Blue, Green-B, Green-C, Green-D, Green-E）の車両位置・到着予測・運行アラートを、prod では 1 分ごと、dev では 5 分ごとに取得しなければならない
- **FR-002**: システムは、取得した最新の状態で現在値（車両・予測）を 1 つのトランザクションで入れ替えなければならない
- **FR-003**: システムは、アラートを削除せずに保存し、フィードに出ているかどうか（`in_feed`）と、初めて／最後に観測した時刻を記録しなければならない
- **FR-004**: システムは、車両位置の履歴を、位置が更新された場合だけ保存しなければならない
- **FR-005**: システムは、各便の各駅（親駅）への到着を推定して、推定方法とともに記録しなければならない（定義は data-model.md）
- **FR-006**: システムは、到着予測をリード時間のバケットごとに 1 件だけ保存しなければならない
- **FR-007**: システムは、MBTA API へのリクエストを 1 環境あたり 5 req/分以下に保ち、429 を受けたらリトライしてはならない
- **FR-008**: システムは、前の回の収集が終わっていないときに、次の回を重ねて実行してはならない
- **FR-009**: システムは、各回の実行結果（開始・終了時刻、成否、件数、レート制限の残量、エラー）を記録しなければならない
- **FR-010**: システムは、路線・駅・路線パターンを毎日同期し、未知の駅 ID を記録して次の同期で解決しなければならない
- **FR-011**: システムは、生データを保持期間（prod 28 日 / dev 3 日）を過ぎたら削除しなければならない。ただし集計が済んでいない運行日は削除してはならない
- **FR-012**: システムは、MBTA API キーが設定されていればそれを使い、設定されていなければキーなしで動かなければならない

### テスト要件（Testing Requirements）

テストでは実 API を呼ばない。DB を使うテストは本物の PostgreSQL 16 で行う。現在時刻は固定する。

- **TR-001（応答の解析）**: 各エンドポイントの記録済みフィクスチャを解析・変換し、期待するドメインの値になることを確かめる。次の特殊ケースは専用のフィクスチャで確かめる: 運行時間外の空の応答、終点駅の番線 ID（`Alewife-01` など）、`stop` が `null` の車両、`updated_at` が 30 分前の車両、`UPCOMING` のアラート、`CANCELLED` / `SKIPPED` / 始発駅（到着時刻なし）の予測、`Shuttle-*` の路線パターン、スキーマに合わない行（スキップされ、ジョブは成功する）
- **TR-002（到着検出）**: 到着検出の 3 つの方法（`stopped_at` / `predicted_last` / `interpolated`）と、更新の止まった車両・非営業の車両の除外を、入力と期待値の表で確かめる。「便と親駅の組で到着は 1 件」をプロパティベーステストで確かめる
- **TR-003（予測のサンプリング）**: 到着の 16 分前から 0 分前まで 1 分ごとの予測を入れ、バケットごとに最初の 1 件だけが残ることを確かめる
- **TR-004（運行日と時刻）**: 深夜 0〜3 時の運行日、夏時間の開始日・終了日、`-04:00` / `-05:00` のオフセットを確かめる
- **TR-005（再生テスト）**: 実 API の連続ポーリング（30 回以上。運行開始の時間帯と日中を含む）の記録を collector に順に流し、`arrival_events`・`prediction_samples`・`vehicle_positions` の最終状態が期待値と一致することを確かめる。同じ回を 2 回流しても行が増えないことも確かめる
- **TR-006（DB の書き込み）**: 現在値の入れ替えがトランザクションで行われること（途中で失敗したら前の状態が残る）、2 つの collector を同時に動かすと後の方がすぐ終わることを確かめる
- **TR-007（保持期間）**: パーティションの作成、保持期間を過ぎたパーティションの削除、集計が済んでいない日のパーティションが残ることを確かめる
- **TR-008（レート制限）**: 429 を受けたときにリトライせず失敗として記録されること、1 回の収集のリクエスト数が 3 であることを確かめる

### 主なエンティティ（Key Entities）

- **路線（Route）**: 対象 8 路線。色、方向名、行先
- **駅（Stop）**: 親駅（`place-xxxx`）とホーム。ホームは親駅に属する
- **路線パターン（Route Pattern）**: 方向ごとの停車順と形状
- **車両（Vehicle）**: 現在位置、状態、走行中の便、最終更新時刻
- **到着予測（Prediction）**: 便・駅ごとの予測到着／出発時刻、種類、不確かさ
- **アラート（Alert）**: 影響（effect）、原因（cause）、重要度、有効期間、対象の路線・駅
- **到着イベント（Arrival Event）**: 便・親駅ごとの推定到着時刻と推定方法
- **予測サンプル（Prediction Sample）**: リード時間のバケットごとの予測
- **収集の実行記録（Collector Run）**

## 成功基準（Success Criteria）*（必須）*

### 測定できる成果（Measurable Outcomes）

（初期値。運用を始めてから見直す）

- **SC-001**: prod で、1 日にスケジュールされた収集のうち 99% 以上が成功する
- **SC-002**: 運行時間中、現在値テーブルのデータは 2 分より古くならない（p95）
- **SC-003**: MBTA API へのリクエストは、どの 1 分間をとっても 1 環境あたり 5 件以下
- **SC-004**: 収集 1 回の所要時間は 50 秒未満（p99）
- **SC-005**: 生データ（28 日分）と集計データを合わせて、Cloud SQL の最小構成（10GB）に収まる

## 前提条件（Assumptions）

- 到着時刻は車両位置から推定するため、1 分間隔の収集では精度が ±60 秒程度になる。dev（5 分間隔）の精度はさらに低い
- 開発の初期は MBTA API キーなしで動かす。prod の稼働前にキーを取得する（`specs/004-infra-cicd/`）
- 運行日は `America/New_York` の時刻から 3 時間引いた日付とする
