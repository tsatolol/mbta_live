# 調査と決定: データ収集

各決定について、決定・理由・検討した代替案を記録する。

## 収集方式: 定期ポーリング

- **決定**: Cloud Scheduler が Cloud Run Job（collector）を prod は 1 分ごと、dev は 5 分ごとに起動する
- **理由**: 分析用途なので、誰も画面を見ていない時間も収集し続ける必要がある。ジョブ型は失敗しても次の回で回復し、常時起動のコストがかからない
- **検討した代替案**: MBTA API の Server-Sent Events を常駐ワーカーで購読（高頻度だが Cloud Run の常時起動が必要でコスト増）／画面を開いたときだけ取得（履歴が残らず分析できない）

## 収集間隔と保持期間

- **決定**: prod は 1 分間隔・生データ 28 日保持、dev は 5 分間隔・3 日保持。日次集計は無期限
- **理由**: Cloud Scheduler の最小単位が 1 分。生データは再集計に必要な期間だけ残し、長期の傾向は集計テーブルで見る
- **検討した代替案**: 30 秒間隔（ジョブ内で 2 回取る工夫が必要。キーなしではレート制限が厳しい）、90 日保持（当初案。ユーザーの判断で 28 日に短縮）

## MBTA API キー

- **決定**: 開発の初期はキーなしで動かす。prod の稼働前にキーを取得し、dev / prod で別のキーを使う
- **理由**: キーなしの上限は送信元 IP 単位で 20 req/分。Cloud Run の送信元 IP は他の GCP 利用者と共有されるため、他人に使い切られて 429 になる可能性がある
- **検討した代替案**: Cloud NAT で固定 IP を持つ（コスト増。キーを取れば不要）

## 予測の保存量

- **決定**: リード時間のバケット（1, 3, 5, 10, 15 分）ごとに、便・駅あたり 1 件だけ保存する
- **理由**: 全件を毎分保存すると 28 日でも数千万行規模になる。予測精度の分析にはリード時間ごとの代表値があれば十分

## 実到着の推定

- **決定**: 車両の `STOPPED_AT` を第一に使い、取りこぼした駅は直前の予測、それもなければ線形補間で補う。推定方法を `source` として残す
- **理由**: MBTA API は実際の到着時刻を返さない。1 分間隔では短い停車を取りこぼすので、補完が必要。精度の低い `interpolated` は予測精度の集計から外せるように区別する

## ORM: Prisma

- **決定**: Prisma ORM（Prisma Migrate）を使う（当初案の Drizzle から、ユーザーの判断で変更）
- **理由**: アプリ側の通常の読み書きを型安全に書ける
- **トレードオフ**: パーティション、分析用の集計クエリ（`percentile_cont`、ウィンドウ関数）、大量の upsert は Prisma の API で表現できない。それぞれ手書きのマイグレーション SQL、TypedSQL（`prisma/sql/*.sql`）、`$executeRaw` で補う（data-model.md）
- **検証結果**（2026-11-02）: パーティションの子テーブルを別スキーマ `partitions` に置いても、`prisma migrate dev` は drift を出さない（「Already in sync」）。`tests/integration/prisma-drift.test.ts` で継続して確かめる
- **バージョン**: Prisma 7.10（安定版）。npm の latest は 8.0 の RC だったので使わない

## 生データの削除方法

- **決定**: 日ごとのパーティションにして、パーティションごと `DROP` する。集計が済んでいない日は削除しない
- **理由**: `DELETE` より速く、テーブルの肥大化（bloat）が起きない。集計ジョブが失敗し続けても生データを失わない

## 静的データの取り方

- **決定**: `/stops` は 2 段階で取る（route_type で絞ってホームと親駅 → 親駅の child_stops で終点駅の番線などを補う）。それでも見つからない ID は記録して次の同期で取る
- **理由**: 実測で、route_type で絞った結果に終点駅の番線など 12 件が含まれないことを確認した。詳細は contracts/mbta-api.md
